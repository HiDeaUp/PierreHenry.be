Can your SaaS safely handle a failed API request?

A payment can succeed even when your application sees a timeout. If you retry without knowing what happened, could you accidentally charge someone twice? Here's how to reproduce the failure, inspect the decision, and understand what reliable recovery requires.

The failure you may not have tested

Imagine a customer places an order. Your SaaS sends a payment request. The provider commits the charge, but the network response never reaches your server.

Your application sees a timeout. What should it do now? Retrying with a new operation identifier could produce a second charge. Treating the timeout as a failure could leave the customer charged without an order. Both are bad outcomes.

I've seen how much difference the right decisions around integrations, caching and infrastructure can make to a production system. My starting point isn't adding more technology. It's understanding the failure and choosing the smallest reliable solution.

One important distinction: this is a constructed educational scenario, not a claim about a former client's payment system. The repository uses simulated charges and fictional orders, never real payment details.

Before writing code, check three things

01. Request identity

Does a repeated customer action reuse the original request identity, or create a new order?

02. Provider semantics

Does your external provider guarantee idempotency for repeated operations? For how long and under which conditions?

03. Recovery evidence

Can your system distinguish “failed before processing” from “may have succeeded but response was lost”?

Don't assume a retry library answers these questions. Retries are only safe when the underlying operation has a suitable contract.

Do it yourself

Run the failure and watch what changes

The repository contains a small Node.js application, a browser interface, a simulated payment provider and automated tests. You can inspect the source rather than trusting screenshots.

Requirements: Node.js 22.13+ and a local development environment. No account, API key, payment provider or npm dependencies required.

git clone https://github.com/pH-7/SaaS-Reliability-Showcase.git
cd SaaS-Reliability-Showcase
npm test
npm start
# Open http://127.0.0.1:3000
  1. Explore the unsafe retry. In the browser, choose “Reproduce the unsafe retry”. The illustration shows two provider charges for one customer intention when operations are not identified consistently.
  2. Simulate an ambiguous timeout. Choose “Response lost after provider charges”, create a fictional order, then process it once. The provider records a charge, but the order remains retryable.
  3. Retry the same operation. Process the order again. The provider returns the existing simulated charge and the order completes without another charge.
  4. Try the client request again. Replay the initial order request using the same client key. You should get the existing order, not a second order.
  5. Inspect the evidence. Review the event history, compare attempts to provider-charge count, then run the automated tests and inspect the implementation.

A checklist for your own integration

Before signing off a critical workflow, I would want documented answers to these questions. They apply beyond payments to orders, webhooks, messaging and background jobs.

  • Can the same request be delivered twice without creating duplicate business operations?
  • Does your idempotency key represent the business intention, not just one HTTP attempt?
  • Is reusing the key with a different payload rejected or handled explicitly?
  • Have you checked the provider's actual deduplication guarantees, including key expiry?
  • Can the application represent an unknown outcome without incorrectly marking it failed or completed?
  • Is there a reconciliation process if your database and the external system disagree?
  • Do alerts cover operations that remain unresolved after retry limits are reached?
  • Can you test these cases safely in a sandbox or controlled environment?

If you cannot answer several of these yet, that doesn't automatically mean your architecture is wrong. It means there's something worth investigating before the failure happens in production.

What the demo proves, and what it doesn't

The demonstration shows how stable request and operation identities prevent repeated simulated side effects in one local process. It includes testable states for an unknown response and recovery through a repeat operation.

It does not prove that a real payment provider behaves the same way. The simulated provider shares the application's SQLite database. In production, the external service is a separate system with its own failure modes, key retention policy, reconciliation requirements, webhook semantics, credentials and security obligations.

The most important lesson is not “add an idempotency key and you're done”. It's to establish the actual contract, decide how to handle uncertain outcomes and verify recovery with evidence.
