Flagship systems

The projects with the clearest consulting relevance.

Each project below is presented for what it demonstrates. Prototype, beta and distribution boundaries remain explicit.

01 / Long-lived platform

pH7Builder

A self-hosted community platform carried through thirteen years and more than 11,000 commits. It demonstrates ownership across product evolution, identity, community workflows, moderation, releases and maintenance.

Consulting relevance
Platform evolution, incremental modernisation and founder-led SaaS.
Reusable advantage
Real migration history and long-term maintenance decisions, not a greenfield demonstration.

02 / Embedded AI infrastructure

ToucanDB

A beta, embedded local-first vector database with a framework-neutral RAG pipeline for semantic search, retrieval and application memory. SQLite remains the durable source of truth while FAISS indexes can be rebuilt deterministically.

Consulting relevance
Private RAG, LLM applications, local agents and confidential knowledge products.
Reusable advantage
Namespace isolation, source attribution, bounded context, encryption boundaries and retrieval evaluation in one component.
Inspect ToucanDB on GitHub ↗

03 / Private developer tooling

pH7Console

A macOS command console built with Tauri, Rust and TypeScript. Local intelligence, encrypted history, deterministic fallback behaviour and explicit workspace access keep the operating boundary visible.

Consulting relevance
Local AI, developer tools and privacy-conscious desktop products.
Reusable advantage
Patterns for local model packaging, encrypted adaptive state and user-controlled execution.
Inspect pH7Console on GitHub ↗

04 / On-device product AI

SucceedAI

A private writing assistant for Apple platforms using the operating system's on-device model. Transformations remain user initiated, source and result stay separate, and sensitive text does not require an application server.

Consulting relevance
On-device AI, Apple product development and human-controlled automation.
Reusable advantage
Interaction patterns for stale-context checks, safe replacement, undo and permission-light design.
Inspect SucceedAI on GitHub ↗

05 / Product foundation

Orbit

A strict TypeScript application foundation with routing, APIs, tests and CI. Its purpose is to make product and architecture decisions explicit without introducing a large runtime dependency surface.

Consulting relevance
Early product builds, maintainable web applications and incremental modernisation.
Reusable advantage
A tested starting point that reduces setup time while preserving visible engineering decisions.
Inspect Orbit on GitHub ↗

How the assets work together

From ambiguous workflow to verified production path.

The value is not a collection of reusable code dropped into every engagement. It is a tested way to make the important decisions visible and reuse only what fits.

  1. 01
    Understand

    Define the user, operational and business outcome before selecting the technology.

  2. 02
    Bound

    Make data, permissions, failure modes, AI limits and human decisions explicit.

  3. 03
    Build

    Ship the smallest production path that can test the architecture against reality.

  4. 04
    Verify

    Use tests, evaluations, release evidence and operational checks appropriate to the risk.

  5. 05
    Transfer

    Document the decisions and leave the team able to operate and extend the system.

Where this creates client leverage

Specialised enough to be useful, broad enough to own the product.

AI product delivery

Consequential workflows need more than a model demonstration

Connect the user workflow, system boundaries, evaluation, implementation and release rather than isolating AI from the wider product.

Private AI

Sensitive information needs an intentional architecture

Compare on-device, embedded and service-based approaches against the real data, access, latency and operational constraints.

Platform evolution

Working software needs a safer path forward

Modernise around product value, migration risk and delivery evidence instead of assuming a complete rewrite is the answer.

Engineering enablement

Delivery should improve the team, not create dependency

Combine architecture, implementation, technical explanation and reusable working practices in the same engagement.
